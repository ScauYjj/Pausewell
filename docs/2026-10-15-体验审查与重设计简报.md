# 体验审查与重设计简报

日期：2026-10-15。状态：审查结论与流程评审稿，不是已确认的完整 PRD，也不是新界面的实施完成说明。

## 1. 本轮范围与已确认方向

用户反馈：现有原型的功能细节、交互和设计风格没有提前明确，初次使用难以理解。

本轮实查“打开首页 → 打开新建计划 → 填写一分钟普通提醒草稿”三个步骤，使用本轮新截取的真实窗口画面与 Windows UI Automation 信息。草稿随后取消，没有保存新计划，没有修改提醒开关、已有计划或执行记录，没有修改应用源码。

**用户已确认：设置一次，之后每次打开软件自动恢复提醒。**

“随 Windows 开机启动”仍是单独可选项，不能从上述选择推导为已授权修改系统启动设置。本轮不修改实际运行方式。

## 2. 审查结论

现有程序证明了部分规则与窗口可以运行。它尚未形成清楚、连贯、可自我解释的使用体验。主要缺口是状态表达、任务路径和信息层级，视觉风格也未经用户选择。测试按钮能否工作，不能替代这些设计判断。

### 步骤 1：打开首页，判断是否在提醒

总体情况：主要信息存在，但状态表达不清晰，优先修正。

![步骤1：本轮实查首页](D:/个人资料/Codex/RemiderAPP/artifacts/ux-audit/01-current-home.png)

可见事实：

- 页面显示“已启用的计划 3”，右上按钮为“开始提醒”，底部小字为“提醒已暂停”。
- 首页最醒目位置是欢迎语、较大的装饰性区域及“体验一次活动提醒”。
- 单条计划写“完成后 1 分钟”“等待开始”，没有直接说明首次何时开始。
- 首页和提醒计划都存在新建入口，初次使用没有清楚的引导顺序。

问题与影响：

- 用户需同时理解计划开关、全局开关、办公/会议模式，界面却没有建立这三者的关系。
- “已启用”容易让人判断已经开始提醒。真实暂停状态的字号和位置不足以纠正这个理解。
- 预览、正式运行、新建三个动作并列，初次用户不知道先选哪个。
- 欢迎和风格表达占用较大空间，当前状态、下一次提醒和首次行动不够突出。

保留价值：计划列表、会议到期说明、托盘运行说明已有基础，可以重新组织。

无障碍风险：底部状态较小、对比度偏弱，不能只依赖这一处传达关键状态；未做完整对比度测量或屏幕阅读器验证。

### 步骤 2：打开新建计划，理解需要填写什么

总体情况：表单能填写，但初次负担和反馈时机有问题。

![步骤2：本轮实查空白表单](D:/个人资料/Codex/RemiderAPP/artifacts/ux-audit/02-new-plan-empty.png)

可见事实：

- 用户尚未填写时，页面已显示红色“名称请填写 1 至 80 个字符”。
- 类型与循环方式共用一个标题，要求用户先理解两个不同概念。
- 创建喝水事项时，仍显示包含“药物请录入已有用药要求”的说明标题。
- 有效时段没有启用时，两个灰色时间输入框仍占用空间。
- 简单事项也使用有滚动条的长表单。

问题与影响：

- 打开即报错，把正常的未填写状态表达成失败。
- 用户只是想添加一个喝水提醒，却被要求理解通用规则、时间范围和跨类别说明。
- 关键必填项与可选设置未分层，不清楚最少填什么就能使用。

保留价值：固定显示的时间预览区域有助于解释规则，但内容与实际运行状态需要一致。

无障碍证据：本轮读取到的五个 Edit 控件，自动化可访问 Name 都为空，包含有内部 AutomationId 的名称框。内部标识不能代替面向辅助技术的字段名称。需在重设计时建立标签关联，再进行实际朗读与键盘测试。

### 步骤 3：填写一分钟提醒草稿，判断保存后会怎样

总体情况：数值可编辑，生效语义需要重做。

![步骤3：本轮实查一分钟草稿](D:/个人资料/Codex/RemiderAPP/artifacts/ux-audit/03-one-minute-draft.png)

可见事实：

- 表单显示“喝水”“完成后，间隔一段时间”“1 分钟”。
- 预览显示连续三个具体时刻，下面说明“后续时间以每次实际确认完成为起点”。
- 按钮只写“保存计划”，而当前全局提醒处于暂停状态。

问题与影响：

- 暂停时显示绝对时刻，容易被理解成保存后一定会在那些时刻提醒。
- 连续三个固定时刻与完成后动态重新计算同时出现，需要用户自行消解矛盾。
- “保存计划”没有说明是否开始运行、是否只保存、是否还需要额外操作。

依据代码补充：当前保存动作是写入计划并关闭表单，没有独立的启动结果摘要。此处属于源码确认，不是本轮实际点击保存后的观察。

本轮未保存草稿，故未重新实查本次保存后的完整流程，也未审查提醒弹窗、实际完成或会议恢复。这些不能作为本轮已通过的用户体验结论。

## 3. 优先处理的三个设计问题

1. **状态与生效方式。** 用户必须能看懂软件是否运行、当前计划是否有效、下次何时提醒、暂停何时结束。
2. **从想做一件事到开始提醒的路径。** 首次设置、添加事项、暂停时添加及日常打开需要各自明确的动作和结果。
3. **视觉为任务服务。** 先确定信息优先级与布局，再选择风格。颜色、名称、图标和卡片样式目前都是暂定实现，不能当作用户已认可的设计。

## 4. 核心流程评审稿

以下为拟议流程，除日常打开自动恢复这一点外，尚需评审。此文不授权直接据此改代码。

### A. 第一次使用

1. 只解释一件事：设置提醒后，软件在后台运行，到时提示行动。
2. 选择要提醒的事项。喝水、活动等作为可选模板，不提前混入用户已经启用的真实计划。药物从独立入口设置。
3. 普通事项优先填写三件事：提醒内容、循环时间、提醒方式。工作日、有效时段和其他选项折叠到“更多设置”。
4. 给出一段完整、具体的规则解释。例如“开始后 30 分钟首次提醒；确认完成后，再等 30 分钟”。数值由用户设置，模板数值仅用于软件配置示例。
5. 主动作明确为“保存并开始提醒”。开始后展示成功结果与准确首次时刻，提供一次预览入口。
6. 提醒保持后台运行。首次关闭主窗口时，明确告知仍在托盘运行，并说明在哪里暂停或退出。

### B. 以后再次打开

按用户已确认方式，正常情况下自动恢复已保存的提醒，首页直接说明“提醒中”。无需每天重新寻找开始按钮。

明确暂停和会议要有可见期限，仍在期限内则遵守该选择，到期恢复。永久停用某条计划单独处理，不能通过重新打开软件把已停用的计划偷偷启用。

退出、关机期间无法提醒的事实，放在相关场景说明。药物错过时进入待核实，不把“恢复”解释为应该立即补服。

### C. 已在运行时添加事项

- 主动作写“保存并启用此提醒”。
- 保存结果说明本次新增事项、首次提醒时间和循环语义。
- 不重新设置其他计划的计时，不改变当前会议状态。
- 间隔型只给出可确定的首次时刻，并用完成时间示例解释后续计算，不伪装成固定的未来三个时刻。

### D. 暂停期间添加事项

- 主动作写“保存，保持暂停”，明确显示“恢复后 1 分钟首次提醒”等相对说明。
- 若提供恢复全部提醒的操作，必须说明受影响的计划数量，不能让保存一个事项意外启动所有事项。
- 会议中的保存同样说明会后呈现，不绕过用户当前的免打扰选择。

### E. 每次提醒的处理

- 喝水等事项：明确完成、稍后提醒、进入有期限的会议模式。
- 活动：开始计时，结束后确认，不能把倒计时自动当成实际完成。
- 如厕：允许“当前无需要”，与已完成分开记录。
- 药物：单独核对药物、原计划和既有记录，提供已服用、暂无法处理、未服用、不确定，不提供自动补服建议。
- 所有结果反馈下一步，例如“已记录完成，下一次 16:10”；若不受当前有效时段覆盖，解释顺延时间。

## 5. 首页内容优先级建议

拟议顺序：

1. 当前运行状态及结束时间，例如“提醒中”“会议至 16:00”“暂停至 15:40”。
2. 下一件需要处理的事项、下一次准确时间或还有多久，以及必要动作。
3. 各事项的状态与时刻，可直接调整间隔、停用或编辑。
4. 新增提醒、会议和暂停等常用控制。
5. 历史、进阶设置、预览及说明。

预览不再占据日常首页最显眼的主操作位置。技术验证说明与实现细节移出日常任务区域。欢迎文案可以保留少量，不应排在运行状态之前。

## 6. 设计流程重新分阶段

| 阶段 | 交付物 | 判断标准 |
|---|---|---|
| 需求细化 | 功能行为表：入口、输入、默认值、动作、反馈、异常、退出 | 一个具体场景从头到尾没有未定义的跳步 |
| 低保真交互 | 首次设置、日常首页、新增、提醒、会议、药物各关键状态 | 不解释操作时，也能判断下一步和操作结果 |
| 风格选择 | 同一已确定页面的少量视觉方向 | 内容和行为相同，只比较视觉取舍 |
| 高保真设计 | 选定方向、组件、完整状态及可交互设计稿 | 覆盖暂停、等待、错误、会后、待核实等状态 |
| 实施 | 按已评审设计修改代码 | 逐页比对设计与行为，避免再次自行补设计 |
| 可用性验证 | 用户完成实际任务，记录犹豫、误判与失败 | 以能否独立完成任务为依据，不以按钮测试替代 |

视觉方向尚未生成或选择，本轮不把任何配色当成已确定风格。下一份设计应先展示首次设置、日常首页与新增普通提醒三个低保真页面，便于评审行为和信息层级。
